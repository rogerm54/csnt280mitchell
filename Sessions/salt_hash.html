Better passwords using salts and hashes

Using plain text for storing a password should never be done. Unfortunately, storing passwords in plain text is more common than it should be. Although this page is deprecated, it gives you an idea of how many sites use or used to use questionable password policies.

Salts and Hashes

A properly stored password should be salted and hashed. A salt is some text that is combined with a hash of the password. This combination is then hashed again, and that final hash is what is stored. The salt should be random. A hash is a special encoded form of a string. The key to a hash algorithm is that it generates a string of fixed length that is not reversible. That is, you cannot go in the reverse direction from the hash to obtain the orginal string.

Salts should be random

Salts should be random. That means that they should be some hard to guess text, that is different for each password. The salt should be generated each time a password is stored. A fixed salt is a bad idea, because once it is cracked, all the passwords can be cracked more easily. Tools such as John the Ripper can crack a set of passwords that use a fixed salt far more easily than if random salts are used.

Use appropriate hashes

In any popular database or web programming language, the SHA-512 hashing algorithm is available. This creates hash values consisting of 64 words. On Ubuntu Linux you can install the whois package, and this provides the mkpasswd tool. The mkpasswd tool can be used to generate SHA-512 hashes on the command line: 


$ mkpasswd -m sha-512 jane
$6$OduOv5b3H$ORLrgU5t6QZJUo8Glcdk6UuGvHokfU4cms56WpzoWcYLr./in/tdxdOQDo9lFSdAgug6NXk6MsxlKWb1ySZdV/
$ mkpasswd -m sha-512 deoxyribonucleic_acid
$6$QHk16PVr$BGp9VNCaXWhC7VaHkYz/Xx7juMBZ1rAUfRrCCn31FNL0lCbvSoC4OwAWIRSbIzfcPSMmgqP15uzvjI3JRQmbO.

As you can see, the sha-512 hash would not be work backwards to the original text. Unlike encryption, there is no one-to-one correspondence between the original text and the hashed text.

We will use the encode() and digest() functions to make a plpgsql function that performs a sha-512 hash: 


-- do_hash() function, uses SHA-512 hash 
create or replace function do_hash(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return encode(digest(_mystring,'sha512'),'hex'); 
    end; 
  $func$ 
  language 'plpgsql';

Line 1 is just a comment. Note the syntax is the same as for SQL scripts. In fact, plpgsql functions are defined in SQL scripts.

Line 2 is the function declaration header. Note in the parameter list that the name of the parameter precedes the type of the parameter. So the variable _mystring is of type "text". It is common practice to start variable names with an underscore. That will avoid difficult to fix bugs that occur if you use a variable name that is the same as a database field name.

Line 3 specifies that the return type is "text". Lines 4 and 8 are the double-dollar delimiters that allow the normal use of quotes within. This allows using strings (that are single quoted) in the same way as normal SQL commands.

Line 5 marks the beginning of the function definition. Line 7 marks the end of the function definition. If the function uses local variables, a declare section would be used inside the function definition.

Line 6 is the one instruction in the function definition. Note that instructions end with a semicolon (;). In this function, the digest() function performs a sha-512 hash, and the encode() function converts that hash into a hexadecimal string. The hexadecimal string is what is returned by the function.

Using a salt

A salt is a string that is combined with the password string to make the password harder to guess. The salt should be randomly generated so that a different salt is used for each password. Here is a plpgsql function that builds on the do_hash() function to make use of a salt. 


-- do_hash() function, uses SHA-512 hash 
create or replace function do_hash(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return encode(digest(_mystring,'sha512'),'hex'); 
    end; 
  $func$ 
  language 'plpgsql'; 
  
-- make_salt() function 
create or replace function make_salt(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return do_hash(now() || _mystring); 
    end; 
  $func$ 
  language 'plpgsql';

The new lines, shown with a different background, are lines 11-19. On line 16, the now() function returns a string that corresponds to the current day and time. The || symbol is the concatenation operator in SQL. So, the salt is formed by taking the current date/time string, concatenating it with the passed string and then performing the sha-512 hash on the resulting string.

Creating a salted and hashed password

Next, we create a function for generating a salted and hashed password. 


-- do_hash() function, uses SHA-512 hash 
create or replace function do_hash(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return encode(digest(_mystring,'sha512'),'hex'); 
    end; 
  $func$ 
  language 'plpgsql'; 
  
-- make_salt() function 
create or replace function make_salt(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return do_hash(now() || _mystring); 
    end; 
  $func$ 
  language 'plpgsql'; 
  
-- make_enc_pass() function 
create or replace function make_enc_pass(_mystring text) 
  returns text as 
  $func$ 
    begin 
      return do_hash(_mystring || make_salt(_mystring)); 
    end; 
  $func$ 
  language 'plpgsql';

The new lines, shown with a different background, are lines 21-29. The passed string is concatenated with the salt of the passed string. The resulting string is hashed again. This scheme makes it relatively difficult to guess the password, since the salt is random and unknown, and the amount and type of concatenations that are performed are also unknown.

Storing the password and salt

The following function could be used to store the password and salt into a table named users. It is also assumed that this table has the following fields: username, salt and enc_pass. 


  -- add_user() function 
create or replace function add_user(_user text, _pass text) 
  returns boolean as 
  $func$ 
    begin 
      insert into users (username,salt,enc_pass) values 
        (_user, make_salt(_pass), make_enc_pass(_pass)); 
      return 't'; 
    end; 
  $func$ 
  language 'plpgsql';

We need to store the salt along with the salted and hashed password, because the salt is required to check if the submitted username and password match. Let's create a plpgsql function that can be used to validate a username and password.

A function to validate the username/password

The get_id() plpgsql function will return the user's id if the username and password is valid. Otherwise, this function will return a -1. 


   -- get_id() function 
  create or replace function get_id(_user text, _pass text) 
    returns integer as 
    $func$ 
      declare 
        rec record; 
      begin 
        select into rec * from users where username=_user; 
        if found then 
          if do_hash(_pass || rec.salt) = rec.enc_pass then 
            return rec.id; 
          else 
            return -1; 
          end if; 
        else 
          return -1; 
        end if; 
      end; 
    $func$ 
    language 'plpgsql';

Note that this function returns an integer as specified on line 3. Line 5 starts the declare block where local variables are declared. On line 6, the local variable, rec is defined to be of type "record". The "record" type is a record returned from a database select query.

Lines 8-17 form the definition of the get_id() function. On line 8 we attempt to select all fields into rec from the users table where the username field matches the submitted username. Lines 9-17 define the selection statements that handle the possible cases from this attempt.

The case going from line 9-14 is matched if the username is found in the users table. If this is true, the returned record is stored in the rec variable. Line 10 checks to see if the hash of the submitted password concatenated with the stored salt matches the stored password. If this is true the user's id is returned on line 11.

On lines 12-13, this is matched if the username is valid but the password is not. In this case a -1 is returned on line 13.

Lines 15-16 define the case that deals with the username not being in the users table. In that case, a -1 is returned on line 16.

Note that the get_id() function returns the same value (-1) for a bad username and a correct username with bad password. You may choose to return different values if you want to know the difference.

Putting it all together

You can put all of these plpgsql functions into one SQL script. After including such a script, you could then test these scripts in psql.

Here is a series of steps that could be used to test these plpgsql scripts out. First, create an "init.sql" that creates an appropriate users table: 


-- init.sql
drop table if exists users cascade;
create table users (
  id serial,
  first_name varchar(30),
  last_name varchar(40),
  username varchar(50) unique,
  password text,
  salt text,
  enc_pass text,
  primary key (id)
);

Using PHP instead of plpgsql

Suppose that you are not using PostgreSQL. This means you won't be able to use plpgsql functions. You can make PHP functions that can perform the hashing. These are shown below: 


<?php 
  function do_hash($text) { 
    return hash('sha512',$text); 
  } 
  function make_salt($text) { 
    return do_hash(date('Y-m-d H:i:s') . $text); 
  } 
  function make_enc_pass($text) { 
    return do_hash($text . make_salt($text)); 
  } 
?>

This file would simply have to be included on any PHP script that needs this functionality. It is straightforward to create an add_user() and a get_id() function in PHP. This is left as an exercise for the reader.
